# ドキュメント品質規約

Ideas Repository のフェーズドキュメントが満たすべき構造・整合性・品質の基準を定める。team-hub の `architecture.md` / `coding-rust.md` に相当する、本リポジトリ（ドキュメント／プロセス管理）固有のドメインルール。

phase エージェント・`doc-reviewer`・`gate-checker` はこのルールを判定基準として参照する。

## トレーサビリティ（最重要）

フェーズは前段の成果を入力とする連鎖構造を持つ。各段の要素が前段の要素に追跡可能であること。

```
01-brainstorm   課題・要件概要・未解決疑問点
      │ （課題 → 不確実性）
02-poc-plan     不確実性 → PoC 項目 → 成功基準・Go/No-Go 基準
      │ （PoC 項目 → 検証）
03-poc/<item>   検証結果 → 成功基準との照合
      │ （検証結果 → 根拠）
04-behavior/    ビヘイビア（<PREFIX>-N）← PoC 根拠 / 優先度 / ステータス
      │ （<PREFIX>-N → 実装単位）
05-tasks        タスク（TASK-N）← 対象ビヘイビア / 依存 / 担当 / 工数
      │ （TASK-N → スケジュール）
06-roadmap      マイルストーン ← TASK-N / タイムライン / 着手判定
```

## ビヘイビア SSOT 原則

`04-behavior/` はアイデアの振る舞いの**唯一の正（Single Source of Truth）**である。

- 仕様変更・仕様追加は、必ず `04-behavior/` の該当ファイルの変更・追加から始める。派生物（`05-tasks.md` のタスク、`spec.md`）はその後に更新する。
- 人間・クライアント向け仕様書 `spec.md` は `/generate-spec` で `04-behavior/` から自動生成する。**手書き・直接編集しない**（自動生成ヘッダを保持する）。
- 後続フェーズ・実装がビヘイビアと食い違う場合は、黙って吸収せず `04-behavior/` の更新（または逆戻り提案）で解消する。

### ID 付与と相互参照

- ビヘイビアは `<プレフィクス>-<番号>`（例: `LOGIN-1`）の一意 ID を付与する。プレフィクスは各ファイル冒頭で宣言し、アイデア内で対象領域と 1:1 に対応させる。
- 番号はファイル内通しで、**削除しても再利用しない**（欠番のまま残す。欠番は許容、再利用・重複は不整合）。
- タスクは通し番号 `TASK-N` を付与し、「対象ビヘイビア」欄でビヘイビア ID と紐付ける（`_templates/05-tasks.md` の規約に従う）。基盤タスクは「なし（基盤）」と明記する（孤立タスクを作らない）。
- `05-tasks.md` が参照するビヘイビア ID は `04-behavior/` に実在すること。
- マイルストーンは必ず `TASK-N` を割り当てる（未割当タスクを残さない）。
- 各 Must・確定ビヘイビアは最低 1 つのタスクでカバーされる（未カバービヘイビアを作らない）。

### レガシー形式（`04-requirements.md`）の ID 規約

`04-behavior/` を持たず `04-requirements.md` を持つ既存アイデアには従来の規約を適用する。

- 要件は `REQ-N`、タスクは `TASK-<要件番号>.<連番>`（例: `TASK-1.1`、`REQ-1` に紐付く）。
- 各 Must 要件は最低 1 つのタスクでカバーされる。マイルストーンは `TASK-X.X` を割り当てる。

## テンプレート準拠

- 各フェーズ文書は `_templates/` の対応テンプレート（Phase 4 は `_templates/04-behavior/` 配下、その他は `<NN>-*.md`）の必須節をすべて埋める。
- レガシー形式のアイデアの Phase 4・5 は `_templates/legacy/`（`04-requirements.md` / `05-tasks.md`）を正とする。
- 見出しレベル・リスト記法（`-` / `1.`）・表形式・コードブロック言語タグはファイル単位で揃える。新発明は避ける。
- 既存の同種ファイルを Read してスタイルを踏襲してから書く。

## ビヘイビア・基準のテスト可能性

- ビヘイビアは「**前提 / 操作 / 期待**」の 3 部構成で**測定可能・検証可能**な形で書く。この形式が受け入れ基準を兼ねる。
- 曖昧語を避ける: 「適切な」「高速な」「使いやすい」→ 具体的な数値・条件・操作で表現する。
  - 悪い例: 「レスポンスが高速であること」
  - 良い例: 「95 パーセンタイルのレスポンスが 200ms 以内であること」
- 各ビヘイビアには優先度（Must / Should / Could）とステータス（確定 / 検討中）を付与する。Won't 相当は項目化せず `README.md` の「除外事項」に記録する。
- レガシー形式では受け入れ基準を独立欄で書き、要件に MoSCoW 優先度（Must / Should / Could / Won't）を付与する。

## 判定ゲートの記録

- 判定ゲート（追求判定 / Go-No-Go / スコープ確認 / 着手判定）の結果は、該当フェーズ文書末尾の「判定」節に `結果 / 理由 / 日付` で記録する。
- 詳細は [`phase-gate.md`](phase-gate.md) に従う。

## ステータス整合

- `README.md` のステータステーブルは常に現状と一致させる。記号は [`convention.md`](convention.md) のステータス記号節に従う。
- 逆戻り時は戻り先フェーズを「🔁 再検討中」、それ以降を「⬜ 未着手」または「🔁 再検討中」に戻す。

## 日本語・表記

- 本文はですます調。用語統一・表記細則は [`japanese.md`](japanese.md) に従う。

## レビュー観点（doc-reviewer 用チェックリスト）

| カテゴリ | 確認内容 |
|---------|---------|
| トレーサビリティ | フェーズ連鎖が保たれ、ID 相互参照が一貫しているか／未カバービヘイビア（レガシー: 要件）・孤立タスク・未割当タスクがないか／ID の再利用・重複がないか（欠番は許容）／参照先 ID が実在するか |
| テンプレ準拠 | 必須節が埋まり、スタイルが揃っているか |
| テスト可能性 | ビヘイビア（前提・操作・期待）・成功基準が測定可能か／曖昧語を排しているか |
| 優先度 | 新形式: 優先度（Must/Should/Could）とステータス（確定/検討中）が付与されているか／レガシー: MoSCoW が付与されているか（ステータス欄は不要） |
| SSOT | 仕様変更が `04-behavior/` 起点になっているか／`spec.md` が手書き・直接編集されていないか |
| 判定ゲート | 該当フェーズで「判定」節が記録されているか |
| ステータス | README のステータス記号が現状と整合しているか |
| 日本語 | ですます調・用語統一・表記細則に沿っているか |
